식이 가이드라인 지식 DB 구조

식이 질문과 목표가 어떤 지침의 어느 권고를 근거로 만들어졌는지 추적하기 위한 전체 구조입니다.

최종 업데이트 2026-10-20 11:17 KST데이터 기준 식이 개발전달 데이터계약 v1.0.0근거 기준 식이 의학근거대조 v1.0.0
핵심 원칙　원문 문서를 그대로 화면 문구로 쓰지 않고, 권고문을 한 건씩 구조화한 뒤 식이 축·질문·목표에 연결합니다.

0. 전반적인 운영 구조

1공식 자료 수집WHO·정부·학회·전문기관의 문서와 개정판을 등록합니다.
2권고 분해문서의 권고를 행동 하나씩 나누고 원문 위치를 남깁니다.
3적용 범위 판단일반인·질환별 대상, 제외 조건과 안전 제한을 분리합니다.
4서비스 구조로 변환식이 개념을 8개 축과 질환·검진 신호에 연결합니다.
5질문·목표 연결회전 질문, 선택지 3개와 목표 문구에 근거 ID를 붙입니다.
6운영·갱신실행 이력을 남기고 개정판이 나오면 영향 항목을 다시 점검합니다.
사용자 화면에는 자연스러운 질문과 목표만 보입니다. 가이드라인명·원문·매핑 사유·안전 조건은 관리자 지식 DB에서 추적합니다.

1. 전체 식이 DB에서 결과가 만들어지는 과정

식이 DB는 참조 24개·런타임 14개·관리 1개, 총 39개 논리 테이블로 정의되어 있습니다. 엔진은 기준 데이터와 사용자별 실행 데이터를 함께 읽어 그날의 질문과 목표를 만들고, 결과와 선택 근거를 다시 런타임 DB에 저장합니다.

참조 DB 24개① 바뀌는 기준값

질문·선택지·질환·검진·목표·노출 조건·설정값을 버전과 함께 관리합니다.

diet_questiondiet_disease_rulescreening_diet_signaldiet_goal_phrase
런타임 DB 14개② 사용자·세션 기록

직접 선택 질환, 진료정보 확인, 검진 결과, 답변과 이전 목표를 사용자·날짜별로 저장합니다.

diet_sessiondiet_answeruser_condition_selectionscreening_result
관리 규칙 1개 + 선정 엔진③ 규칙 결합·후보 선정

대상 끼니를 정하고 질문 축을 회전시킨 뒤 안전·시간·달력 조건을 통과한 목표를 고릅니다.

diet_implementation_rulediet_rule_parameterdiet_phrase_applicability
결과 DB④ 결과와 근거 저장

실제 질문, 유효 답변, 축 상태, 목표 문구 스냅샷과 완료 여부를 남깁니다.

diet_question_statediet_axis_snapshotdiet_goaldiet_goal_completion

하루 결과 생성 순서

세션 생성사용자 현지 날짜를 04시 경계로 묶고 앱 진입 시각을 저장합니다.diet_session
입력값 결합직접 선택 질환을 먼저 보고, 확인된 진료정보와 3개월 이내 검진 신호를 합쳐 중복을 제거합니다.user_condition_selection
대상 끼니 결정00~10시는 어제 저녁, 10~12시는 오늘 아침, 12~17시는 오늘 점심, 17~24시는 오늘 저녁을 대상으로 합니다.R-02
오늘 질문 계획질환 확인이 필요하면 확인 질문부터 냅니다. 그 외에는 공통 고정 질문과 회전 질문을 계획합니다.diet_question_state
회전 축 선택연결 축 중 최근 28일 유효 답변이 적고, 오래 묻지 않은 축을 우선합니다. 한 순환 뒤에는 일반 축을 포함합니다.R-09 · CFG-041
응답·끼니 시각 저장선택지 답을 저장합니다. 평소 또는 적게 먹었고 건강 앱 식사 기록이 없으면 시각 단계가 최대 1개 추가됩니다.diet_answer · diet_meal_time
축 상태·단계 계산최근 응답으로 관찰 중·개선 필요·보통·양호를 계산하고 목표 단계를 입문·기본·도전으로 관리합니다.diet_axis_snapshot · diet_axis_stage
목표 선정·저장회복 → 수면 부담 → 오늘 회전 축 순으로 후보를 만들고, 질환 안전·시간·달력 조건과 최근 노출 이력을 적용합니다.diet_goal
질문 수 해석　핵심 식이 질문은 세션당 최대 2개입니다. 식사량 답에 따라 끼니 시각을 확인해야 하면 같은 흐름 안에서 시각 단계가 최대 1개 추가되어, 데이터 계약상 식이 상호작용은 최대 3개가 될 수 있습니다.

2. DB 안에서 근거가 연결되는 방식

① 출처

가이드라인 문서

기관, 문서명, 발행일, 버전, 원문 URL, 검토일

② 근거 단위

권고문

원문 위치, 권고 내용, 적용 대상, 제외 조건

③ 의미 정규화

식이 개념

나트륨, 채소, 단 음료, 단백질, 불포화지방 등

④ 서비스 연결

식이 축

현재 사용하는 8개 관찰 축과 질환·검진 신호 매핑

⑤ 사용자 경험

질문·목표

회전 질문, 선택지 3개, 목표 문구, 안전·노출 조건

4. 가이드라인 지식 DB는 세 영역으로 분리

A. 근거 지식

  • 가이드라인 문서와 절·표 위치
  • 원자 단위 권고문
  • 적용 대상·제외 조건
  • 표준 식이 개념과 동의어

B. 제품 매핑

  • 8개 식이 축
  • 질환·검진 신호 연결
  • 질문·목표와 근거 연결
  • 안전·노출·우선순위 규칙

C. 운영 이력

  • 활성·종료 상태
  • 최근 검토일과 대체 권고
  • 변경 사유와 영향 항목
  • 사용자 응답 이력은 별도 저장

6. 실제 조회 예시

예: 당뇨병 사용자의 단 음료 질문

  1. 당뇨병에 연결된 권고문을 찾습니다.
  2. 권고문의 식이 개념 중 첨가당·가당음료를 확인합니다.
  3. 개념과 연결된 단 음료·간식 축을 가져옵니다.
  4. 그 축의 회전 질문과 목표 후보를 조회합니다.
  5. 안전·노출 조건을 통과한 문구만 화면에 사용합니다.

개발 조회 경로

goal_phrase → goal_phrase_recommendation_map → recommendation → guideline_section → guideline_document

목표 문구 하나에서 원문 문서와 정확한 절 위치까지 역추적할 수 있습니다.

저장 원문, 해석, 대상, 제외 조건, 연결 사유, 검토일
저장하지 않음 사용자 응답·질환 이력 같은 개인 데이터는 이 지식 DB에 섞지 않습니다.

7. 운영 기준

권고 1건 = 행 1개한 문장에 행동이 여러 개면 분리합니다.
원문과 제품 문구 분리사용자용 문구를 원문 칸에 덮어쓰지 않습니다.
근거 등급은 원문 값만출처가 등급을 제시할 때만 선택 필드로 저장합니다.
변경은 대체 관계로 관리삭제보다 비활성화와 supersedes_id를 사용합니다.
최소 검토 필드is_active · last_reviewed_at · supersedes_id를 둡니다.
출처 위치 필수URL만 두지 않고 장·절·표·페이지를 기록합니다.
수치와 단위 분리예: 2,000과 mg/day를 별도 칼럼에 저장합니다.
개인화 규칙은 제품 영역질환 우선순위·3개월 유효기간은 원문과 분리합니다.
